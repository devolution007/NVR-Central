# Campus tunnels (WireGuard)

**Status: generated and unit tested, NOT verified end to end.** No tunnel has been brought up between a real hub and a
real campus device. Treat every step below as a procedure to validate, not a proven recipe.

## Why

The test NVR could not be reached by Dahua P2P (docs/p2p-compatibility.md), but it answers fully over its LAN interfaces
(docs/nvr-capabilities.md). A tunnel makes a campus LAN reachable from the server without opening any port at the campus,
which also works behind NAT and CGNAT because the campus dials out.

## Design

```text
Campus LAN                              Server (public IP, UDP 51820)
 NVR 192.168.15.6 <-LAN-> [connector] ==WireGuard==> [hub 10.77.0.1] -> worker -> NVR at 10.77.<N>.6
```

- One `/16` tunnel network `10.77.0.0/16`. Hub is `10.77.0.1`.
- Each campus gets a **slot** N (1 to 253): tunnel address `10.77.0.<N+1>` and, for connectors, a virtual LAN
  `10.77.<N>.0/24`.
- **Connector mode** maps the virtual range 1:1 onto the real campus `/24` with iptables NETMAP and masquerades, so
  campuses that all use `192.168.1.0/24` do not collide. You register the NVR in the app at `10.77.<N>.<last octet of
  its real address>`.
- **Router mode**: the campus router holds the tunnel and its real LAN is routed directly. Real LANs of router-mode
  campuses must not overlap (the app refuses overlapping ones). Register the NVR at its real LAN address.
- Peer private keys are never stored. Either the server generates a keypair and shows the config once, or the peer
  supplies its own public key (recommended for routers).
- The server keeps each peer's pre-shared key (encrypted) because the hub config needs it.
- Only `/24` private IPv4 campus LANs are supported in this version.

## Settings (.env)

| Key | Meaning |
|---|---|
| `WG_HUB_PRIVATE_KEY` | Hub key, generated by `scripts/init-env.py`. The public key is shown on the Connectivity page |
| `WG_HUB_ENDPOINT` | Public `host:port` campuses dial, for example `vpn.example.com:51820` |
| `WG_INTERFACE` | Interface name for `wg show` (default `wg0`) |
| `WG_HUB_CONF_PATH` | If set, the app rewrites the hub `wg0.conf` there whenever peers change |

## Deploying the hub (UNVERIFIED)

Needs a Linux host with a public IP and UDP 51820 reachable. A PC behind NAT cannot be the hub.

```bash
docker compose -f docker-compose.yml -f docker-compose.tunnel.yml --profile app up -d --build
```

1. Set `WG_HUB_ENDPOINT` and restart the backend.
2. Connectivity page: **Add campus tunnel**. Choose connector or router, enter the campus LAN as a `/24`.
3. Copy or download the shown configuration immediately. It is not retrievable later.
4. The app writes `infrastructure/wireguard/wg0.conf`. **The hub does not reload on its own**: restart the `wireguard`
   container (or run `wg syncconf wg0 <(wg-quick strip wg0)` inside it) after every add or revoke.
5. On the campus device (Linux connector): install `wireguard-tools`, save the file as `/etc/wireguard/wg0.conf`, edit
   `eth0` in the PostUp lines to the connector's LAN interface, then `wg-quick up wg0` and
   `systemctl enable wg-quick@wg0`.
6. Register the NVR at its tunnel address (connector) or real LAN address (router) and run **Test connection**.

## Tunnel health

The worker runs `wg show <interface> dump` every minute and stores the last handshake and byte counters. This only works
when the worker shares the hub's network namespace (the overlay file does that) and has `wg` installed (the backend image
does). Otherwise peers show **Unknown**, which is deliberately different from down.

## Not yet proven

- That the generated hub and connector configs actually bring a tunnel up.
- NETMAP plus masquerade carrying HTTP and RTSP to a real NVR, including RTSP media, not just the control connection.
- Handshake reading from inside the compose overlay (`network_mode: service:wireguard`).
- Reload behaviour of the hub after config changes.
- Throughput and the live-view limits over a real campus uplink (Phase 3).
- Raspberry Pi or mini PC connector images (not built; the config is plain `wg-quick`).

Key derivation is verified against the RFC 7748 Curve25519 test vector, and the `wg show ... dump` parser, address
allocation, overlap rules, revoke and config text are unit tested.
